# Future GitHub sources — contract only

**No remote transport, importer, update job or remote integration test is operational.** GitHubProvider.operational is false; unsupported provider methods raise a deferred error. Appearance offers a working local collection importer and an explicit text notice about unavailable GitHub sources. It does not accept a URL and pretend a remote source is installed.

## Identity, record and UI contract

A future Add URL flow must validate a public HTTPS GitHub URL, resolve a requested ref, preview the bounded collection and pack diagnostics, then let the user select packs and update policies before installation. Provider discovery, validation, staging, installation and update-check results stay behind a provider boundary. QML receives catalog/operation records through Core.Theme and never understands GitHub APIs, directories or subprocesses.

Supported URL forms: `https://github.com/owner/repository`, optional `.git`, optional single trailing slash. Canonical owner/repository casing is lowercased for identity. Ref selection is a separate validated field, not a `/tree/…` URL. Reject other hosts, protocols, embedded credentials, ports, query/fragment, empty/ambiguous components, traversal, encoded path ambiguity and extra paths. Private repositories/authentication, enterprise GitHub hosts, arbitrary redirects and non-GitHub hosts remain deferred. A future HTTP implementation must allow redirects only within an explicitly documented GitHub/API/raw-content host allowlist and bind every content fetch to the resolved revision; it must reject redirects outside that policy and never forward credentials to another host.

[sources.schema.json](../../quickshell/schemas/sources.schema.json) records schema version, provider, canonical URL, stable `github-<hash>` source ID, requested ref/pinned revision, resolved immutable revision, selected pack IDs, autoUpdate, last-check/result, installed version/revision, provenance and error status. Optional packPolicies adds per-pack autoUpdate, followActive, pin, installed version/revision and error. source and selected pack IDs are distinct. Runtime identities are `github-<source-hash>:<pack-id>` so equal pack IDs from different sources cannot overwrite each other. A hash-prefix collision must be rejected when its canonical URL differs. Hashes provide consistency/integrity checks, not publisher authentication.

Future source-management UI needs selected/installed packs, last result/error, pins, check-now, per-pack follow-active policy, rollback and safe remove-source behavior. Removing a source must first preserve the active/rollback snapshot as detached local content or require another usable local selection. It must not delete the sole usable theme, its assets, preferences or overrides. Source display names are not identities.

## Consistent snapshot and installation

1. Resolve a ref to one immutable 40-hex revision. Validate requested refs as data and pass them to APIs as structured values. Never interpolate them into shell commands. Avoid executing repository code or invoking Git hooks; the transport is not a general checkout executor.
2. Read catalog.json, all selected manifests and declared assets from exactly that revision. Honor content/collection/decoded-image/request/cache bounds before use. Verify manifest hashes where supplied. Revalidate staged copies and never combine files from different revisions.
3. Validate packs independently. One broken new pack does not remove unrelated installed valid packs. Preserve old installed versions on deletion, rename, incompatible schema, corrupt images/palette, unavailable refs, offline failures or partial results. Deletion/rename requires an explicit identity decision, not an automatic active-theme switch.
4. Install validated immutable snapshots through the local provider/storage transaction boundary. Unchanged content is an idempotent no-op. Update inactive packs' installed content without activating them. Active packs advance only through a saved followActive/autoUpdate policy, with mode, compatible wallpaper ID and local overrides preserved; pins/opt-outs do not advance.
5. Activation uses the same lock, complete snapshot, compositor baseline comparison, journal and rollback protocol. Update results must say installed versus activated versus retained-with-error. Keep last-known-good installed content and offer rollback. Never turn a failed update into deletion or an unrelated theme selection.

The working portable collection is [examples/material-collection](../../examples/material-collection/catalog.json). One source may list multiple packs in its catalog. The current LocalProvider is the functional implementation of discovery→validation→staging→installation. The future GitHub provider is intentionally a non-operational boundary, not a simulated updater.

## Proposed network policy, not scheduled behavior

Startup must load local resolved snapshots immediately and never await network access. A future startup check may queue after 30–120 seconds of jitter if a source's last check is older than six hours. Normal eligible-source checks should have a minimum six-hour interval, with a global daily request budget (for example 200 requests) and per-run budget (for example 40). Manual requests may bypass age but must deduplicate against an existing check and honor rate limits/budgets.

Use conditional requests/ETags where supported. Proposed timeout budgets: 5 seconds to connect, 15 seconds per metadata/content request, 90 seconds per source run. Cancellation aborts outstanding transport and removes its staging directory; it never interrupts a committed activation halfway through. Use exponential backoff from 15 minutes up to 24 hours, full jitter and server rate-limit/reset signals. Offline means keep local content and record an outcome, not a blocking modal at startup. Bound cached metadata/assets to the current installed/rollback snapshots plus a limited retry cache; age/size eviction must not remove referenced assets. Persist checks/outcomes only once per completed run; background unchanged/non-actionable outcomes stay quiet unless the user saved a notification preference.

These numbers are a design contract to review when implementing transport. No timers, background jobs, authentication setup, downloads, cloning/fetching of theme sources, repository creation, hosting, pushes or publication were executed here.

## Deferred test plan

Remote tests remain unexecuted. A future authorized implementation needs fake HTTP and actual authorized provider tests for URL/redirect/credential boundaries, ref races and immutable revision reads, conditional requests, rate limiting, budgets/timeouts, cancellation/deduplication, cache eviction, offline startup, corrupt/oversized assets, duplicate namespaces, independent pack errors, removed/renamed packs, unsupported schemas, partial downloads, unchanged content, opted-out/pinned packs, active follow policy, preservation of mode/wallpaper/overrides, failed activation/rollback, source removal and publisher provenance display. Existing pure schema/URL-contract fixtures are not evidence that remote importing or updating works.
